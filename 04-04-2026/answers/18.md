
### RCA: ClickHouse OOM from memory-expensive agent query patterns with no per-query resource budget

#### TL;DR

An LLM agent generated a pathological ClickHouse query: a `FULL OUTER JOIN` between `otel_logs` and `otel_traces` on `DATE(Timestamp)`, which created a massive per-day cross-product and exhausted memory. The `queryOtel` tool had no per-query memory budget, and its validation layer was syntax-only, so the query was allowed to run. 20 agents in parallel likely amplified the blast radius, but the specific OOM was caused by this join pattern, not just by missing timestamp filters or broad scans.

#### What Broke and Why

**1. `queryOtel` was created without server-side query isolation**

The original file shipped with only two safeguards: a `LIMIT 500` appended if the agent omitted one, and `max_execution_time: 30`. The schema description said "Include time filter and LIMIT" but this was advisory — no server-side enforcement:

```diff
+const schema = z.object({
+    intent: z.string().describe('What you are looking for'),
+    sql: z
+        .string()
+        .describe(
+            'ClickHouse SQL query for otel_logs or otel_traces. Include time filter and LIMIT.',
+        ),
+});
+
+async function executeQuery(sql: string, agentName: string) {
+    let query = sql.trim().replace(/;$/, '');
+    if (!/\bLIMIT\b/i.test(query)) {
+        query += ' LIMIT 500';
+    }
+
+    const client = await connectClickhouse();
+    const result = await client.query({
+        query,
+        format: 'JSONEachRow',
+        clickhouse_settings: { max_execution_time: 30 },
+    });
```

No `additional_table_filters`, no `max_memory_usage` and no service scoping is specified.

**2. Agents could issue memory-expensive queries against full production data**

Since the tool applies no server-side constraints, agents could issue broad and expensive queries. Some queries lacked timestamp filters, but the specific OOM here came from a `FULL OUTER JOIN ON DATE(...)` query that still had a timestamp predicate and was catastrophically expensive anyway:

```
[MultiHypothesisResearchAgent] queryOtel {
  sqlPreview: 'SELECT Timestamp, SpanName, SpanKind, toString(SpanAttributes)\n' +
    'FROM otel_traces \n' +
    "WHERE ServiceName = 'mewtwo'\n" +
    "AND Timestamp BETWEEN '2026-01-16 23:20:00' AND '2026-01-16 23:30:00'\n" +
    "AND SpanKind = 'Clie..."
}

[MultiHypothesisResearchAgent] queryOtel {
  sqlPreview: "SELECT \n    Timestamp,\n    SpanId,\n    SpanName,\n    StatusCode,\n" +
    "    StatusMessage\n" +
    "FROM otel_traces \n" +
    "WHERE StatusMessage LIKE '%E11000%'\n"   // no timestamp filter at all
}
```

`toString(SpanAttributes)` and `SpanAttributes['key']` access the Map column, which requires per-row deserialization. JOINs on `otel_traces` materialize the right side entirely in server RAM (`FillingRightJoinSide`). Without a Timestamp filter the ClickHouse engine cannot prune the January partition; it reads the full `202601-3_0_481809_555` part.

**3. The workflow multiplied the load 4-5× by setting MAX_CONCURRENCY=20**

```diff
+            max_concurrency:
+                description: 'Max concurrent evals (higher = faster)'
+                required: false
+                default: '20'
...
+                  MAX_CONCURRENCY="${{ github.event.inputs.max_concurrency || '20' }}"
+                  yarn mewtwo run eval run ... -m "$MAX_CONCURRENCY"
```

Both the `workflow_dispatch` input default and the shell fallback were `'20'`, so every execution path — interactive and non-interactive — launched 20 agents simultaneously. At the moment of the first memory kill (`2026-01-30 20:48:40 UTC`), 65 unique eval trace IDs were active within a 20-second window. All were issuing queries to the same ClickHouse server with no per-query memory budget.

**4. OvercommitTracker kills begin**

With 20+ agents simultaneously reading large partitions and materializing JOINs, server RSS hit the 28.80 GiB ceiling:

```
[MultiHypothesisResearchAgent] queryOtel error {
  errorMessage: '(total) memory limit exceeded: would use 28.80 GiB
    (attempt to allocate chunk of 4.31 MiB bytes), current RSS: 28.80 GiB,
    maximum: 28.80 GiB. OvercommitTracker decision: Query was selected to
    stop by OvercommitTracker: While executing MergeTreeSelect(...)'
}
```

The agents retried against the already-saturated server, producing repeated kills from `20:48:40` through `21:40:10 UTC`.

#### Minimal Fix

Two changes to `executeQuery` in `query-otel.tool.ts`:

**1. Add per-query resource caps**

This is the primary fix for the exact OOM here. The failing query already had a `Timestamp` filter, so a lookback-window safeguard alone would not have prevented it.

```typescript
clickhouse_settings: {
    max_execution_time: 30,
    max_bytes_to_read: 5_000_000_000,   // kills at the scan before RAM builds
    max_memory_usage: 2_000_000_000,    // backstop for JOINs / GROUP BY buffers
}
```

**2. Enforce a lookback window if the agent's SQL has no `Timestamp` filter**

```typescript
const LOOKBACK_HOURS = 6;
if (!/\bTimestamp\b/i.test(query)) {
    const anchor = issueTimestamp ? `toDateTime('${issueTimestamp}')` : 'now()';
    const bounds = `Timestamp >= ${anchor} - INTERVAL ${LOOKBACK_HOURS} HOUR AND Timestamp <= ${anchor} + INTERVAL 1 HOUR`;
    query = /\bWHERE\b/i.test(query)
        ? query.replace(/\bWHERE\b/i, `WHERE ${bounds} AND (`) + ')'
        : `${query} WHERE ${bounds}`;
}
```

This lets the MergeTree engine prune entire partitions before any data is read. The anchor is the eval's issue timestamp so the window is centred on the incident rather than on wall-clock now.

**3. Add JOIN guardrails for the LLM/tool**

Reject or rewrite `FULL OUTER JOIN`, `CROSS JOIN`, and `JOIN ON DATE(...)` patterns between `otel_logs` and `otel_traces`; these create huge cross-products even when a timestamp filter is present.

**4. Add per-query table filters where available**

```typescript
clickhouse_settings: {
    max_execution_time: 30,
    max_bytes_to_read: 5_000_000_000,   // kills at the scan before RAM builds
    max_memory_usage: 2_000_000_000,    // backstop for JOINs / GROUP BY buffers
    ...(tableFilters && { additional_table_filters: tableFilters as unknown as never }),
},
```
