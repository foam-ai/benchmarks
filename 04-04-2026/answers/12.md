### RCA: Terminal Velocity Jobs Fail After EBS Volume Exhausted by Accumulating Writable Worktrees

#### TL;DR

The issue solver failed because the EBS volume on the Terminal Velocity EC2 instance was completely full. Every solution job creates a writable git worktree on disk and `cleanup()` intentionally skips removing it, deferring to a "scheduled maintenance" that was never actually implemented. With nothing ever cleaning up, worktrees accumulated indefinitely until the disk hit 100% capacity and even creating a lockfile became impossible.

#### What Broke and Why

Every Terminal Velocity job failed within ~1.5 seconds with the same error:

```
ENOSPC: no space left on device, open '/tmp/tv-lockfiles/worktree-Stream-claims-backend-1da599c41255134baccc9b84e36709526afb114d.lock'
```

This is a two-part design gap.

**`cleanup()` intentionally leaves worktrees behind.** After every job, `terminal-velocity.service.ts:cleanup()` explicitly skips worktree removal, with comments stating they will be handled by "scheduled maintenance after 1 hour":

```typescript
// DO NOT clean up worktree immediately - keep it for reuse
// Worktrees are only removed by scheduled maintenance after 1 hour
if (resources.worktreePath) {
    log().debug('Leaving worktree for scheduled cleanup after 1 hour', {
        worktreePath: resources.worktreePath,
    });
}
```

**No scheduled maintenance exists.** `performMaintenance()` does exist and correctly calls `cleanupOldWorktrees()`, but it is never invoked automatically. Its only call sites are a manual CLI command (`yarn tv-worker maintenance`) and unit tests. There is no `setInterval`, no cron job, no BullMQ repeatable job, and no ECS scheduled task that triggers it. The in-memory maintenance worker handles lockfiles, git gc, and touch operations — but never the top-level worktree cleanup.

The result: every job writes a worktree to `/mnt/ebs/tv-worktrees/{customerId}/{repo}/{sha}-writable-{runId}/`, nothing ever removes them, and they accumulate until the disk is full.

Note: Terminal Velocity runs on EC2 (not Fargate) because it requires Docker-in-Docker (DinD) with `privileged: true` — a capability Fargate does not support. The EBS volume is mounted at `/mnt/ebs/` on the EC2 instance, which is why filling it with worktrees causes ENOSPC even on paths like `/tmp/tv-lockfiles/` that share the same underlying storage.

#### Evidence from Logs

The logs show two separate BullMQ job executions (requestIds `cc6d2816` and `51b01950`) for the same runId, each exhausting all 3 retry attempts — 6 failures in total. Every single one fails identically within ~1.5 seconds of the Terminal Velocity job being submitted, which rules out any logic or timeout issue and points directly at an infrastructure-level block:

```
2025-12-24 20:45:19.329 DEBUG services/issue-solver/mini-solver.ts:290
Submitted Terminal Velocity job { jobId: '33106' }

2025-12-24 20:45:20.812 ERROR services/issue-solver/mini-solver.ts:323
[MiniSolver] Terminal Velocity job failed - failing fast
{ error: "ENOSPC: no space left on device, open '/tmp/tv-lockfiles/worktree-Stream-claims-backend-1da599c41255134baccc9b84e36709526afb114d.lock'" }
```

The ~1.5 second duration (confirmed across all 6 attempts: durations of 1482ms, 1481ms, 1483ms, 1479ms, 1481ms, 1482ms) is consistent with a job that starts, immediately tries to open a file, and fails at the first I/O operation before any meaningful work begins. The system couldn't even write the lockfile — the volume was at 100% before worktree setup even started.

The same SHA (`1da599c41255134baccc9b84e36709526afb114d`) appears in every error, which is the head SHA of the `Stream-claims/backend` repo resolved earlier in the webhook flow:

```
2025-12-24 20:45:10.206 INFO services/issue-solver/factory.ts:237
[ProjectConfig] Using head SHA: 1da599c41255134baccc9b84e36709526afb114d
```

This confirms the worktree path being attempted — `/mnt/ebs/tv-worktrees/68eed2559994b008f8f7b2ee/Stream-claims-backend/1da599c41255134baccc9b84e36709526afb114d` — would have been created by previous runs against the same repo and SHA, and never cleaned up.

#### Fix

**Easiest and Immediate (restore service now):** Delete the affected customer's worktrees directly to unblock jobs:
```bash
sudo rm -rf /mnt/ebs/tv-worktrees/
```

**Permanent:** Change `cleanup()` to actually remove the worktree after job completion. The reuse justification does not hold — each run targets a specific SHA with a unique `*-writable-{runId}` path, so reuse never actually occurs. Removing the worktree in `cleanup()` eliminates accumulation at the source and makes the maintenance dependency irrelevant.

There are many ways to fix this disk space issue. An important detail is that this is happening on the TV worker, which runs on EC2 with EBS-backed storage, not Fargate.
