### RCA: Eval Pre-flight Git Check Fails in Production ECS Container, Job Runs Until 2-Hour Timeout

#### TL;DR

The remote eval dispatch feature forwarded `--sha` commands to ECS workers, but the ECS containers were never set up with the git repository that the `--sha` pre-flight checks depend on. `isWorkingDirectoryClean()` in `mewtwo/eval/utils/git-operations.ts` immediately fails because production containers are deployed as built artifacts with no `.git` directory:

```
Error: Failed to check git status: Error: Command failed: git status --porcelain
fatal: not a git repository (or any of the parent directories): .git
    at isWorkingDirectoryClean (/app/mewtwo/eval/utils/git-operations.ts:21:15)
```

The root cause is **not** the missing child process exit handler. The root cause is that ECS production containers have no git environment — they are built artifacts with no `.git` directory — yet `--sha` commands, which require one, were forwarded to them without any guard. The missing exit handler and the two-hour timeout are both downstream symptoms: the git pre-flight check threw an unhandled error, the child process hung instead of exiting, and the job ran until the worker timeout killed it.

#### What Broke and Why

The bug was introduced in commit `4250670` ("feat: Add Terminal Velocity eval worker for production eval execution #166"), which added remote dispatch to `mewtwo/src/bin/eval.ts` and made it the default. This forwarded `--sha` commands to ECS workers without any check for whether those workers had the git environment the pre-flight checks require:

```typescript
// mewtwo/src/bin/eval.ts — remote is the default (introduced in 4250670)
const shouldRunRemote = !options.local && options.remote !== false;

if (shouldRunRemote) {
    const commandParts = ['yarn eval run', '--local'];
    if (options.sha) {
        options.sha.forEach((sha) => commandParts.push(`--sha ${sha}`));
        // ↑ git-dependent --sha forwarded to ECS without any environment check
    }
    const job = await evalQueue.add('run-eval', {
        command,
        timeout: parseInt(options.timeout),  // default: 7200000ms (2 hours)
    });
}
```

When that command arrives at the ECS worker and re-enters `eval.ts` with `--local --sha`, it immediately hits `isWorkingDirectoryClean()` which runs `git status --porcelain`. This fails instantly in production for two reasons: ECS containers don't have a `.git` directory, and the codebase is deployed as built artifacts, not a git repository:

```typescript
// mewtwo/eval/utils/git-operations.ts
export function isWorkingDirectoryClean(): boolean {
    try {
        const status = execSync('git status --porcelain', { encoding: 'utf-8' });
        return status.trim() === '';
    } catch (error) {
        throw new Error(`Failed to check git status: ${error}`);
    }
}
```

```
Error: Failed to check git status: Error: Command failed: git status --porcelain
fatal: not a git repository (or any of the parent directories): .git
    at isWorkingDirectoryClean (/app/mewtwo/eval/utils/git-operations.ts:21:15)
```

The only other pre-flight check, `verifyInMewtwoDirectory()`, passes silently in ECS because it only checks that the path contains `/mewtwo` and that an `eval/` directory exists — it never checks for `.git`:

```typescript
export function verifyInMewtwoDirectory(): boolean {
    const cwd = process.cwd();
    return cwd.includes('/mewtwo') && fs.existsSync(path.join(cwd, 'eval'));
    // ↑ passes in ECS — no .git check, no warning that git ops will fail
}
```

The worker in `mewtwo/src/workers/eval.worker.ts` has two distinct rejection paths — the `close` handler fires immediately when the child exits non-zero, and the `setTimeout` fires after the full timeout window:

```typescript
// mewtwo/src/workers/eval.worker.ts — two distinct failure paths
child.on('close', async (code) => {
    if (code === 0) { resolve(); }
    else { reject(new Error(`Command failed with exit code ${code}`)); }
    // Path A: fires immediately if child exits — error would be "Command failed with exit code N"
});

if (timeout) {
    setTimeout(() => {
        child.kill();
        reject(new Error(`Command timed out after ${timeout}ms`));
        // Path B: fires after 7200000ms — error is "Command timed out after Nms"
    }, timeout);
}
```

The span data shows `"Command timed out after 7200000ms"` — not `"Command failed with exit code N"`. Since the promise settles on the first `reject` call and ignores subsequent ones, the timeout error is direct proof that the `close` handler never fired — the child hung rather than exiting:

```
2026-01-16 04:56:07.871 ERROR src/workers/eval.worker.ts:130
Eval failed { jobId: '2', error: 'Command timed out after 7200000ms' }

bullmq.job.failed.reason: "Command timed out after 7200000ms"

exception.type:    Error
exception.message: Command timed out after 7200000ms
    at Timeout._onTimeout (mewtwo/src/workers/eval.worker.ts:100)
```

The bug existed from commit `4250670` (January 14) until commit `8dc0689` removed the remote eval execution infrastructure entirely.

#### Fix

The `--sha` flag and its git pre-flight checks must only be dispatched to environments that have a full repository checkout. Either the ECS eval workers need to be provisioned with a git repository, or the remote dispatch path must explicitly reject `--sha` commands before forwarding them to ECS rather than letting them silently hang for two hours.
