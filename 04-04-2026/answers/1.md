### RCA: Tool Ordering Mismatch After OpenAI Token Limit Fallback Exhausts All Retry Attempts

#### TL;DR

The issue solver failed because a two-stage failure chain. OpenAI (`gpt-5-mini-2025-08-07`) hit its input token limit after accumulating 273,263 tokens in the conversation thread, triggering a fallback to `AnthropicBedrockAdapter`. The issue solver had `toolOrder` configured on the thread, which `AnthropicBedrockAdapter` does not support. `BaseLLMAdapter` enforces this at runtime and throws immediately. All three retry attempts failed the same way, and `TerminalVelocityRetry` surfaced the final error after exhausting them. `TerminalVelocityRetryableError` is the retry wrapper — not the root cause.

#### What Broke and Why

The OpenAI path failed first. After 18 turns of parallel tool calls (`file_search`, `github_file_content`, `web_search`), the conversation thread grew to 273,263 tokens — 1,263 tokens over the configured limit of 272,000:

```
2026-01-05 16:39:07.281 ERROR llms/chain.ts:166
Retryable error for gpt-5-mini-2025-08-07:
400 Input tokens exceed the configured limit of 272000 tokens.
Your messages resulted in 273263 tokens.
Please reduce the length of the messages.
```

This error hit three times before `llms/chain.ts` declared max retries exceeded:

```
2026-01-05 16:39:12.038 ERROR llms/chain.ts:170
Maximum retries exceeded for gpt-5-mini-2025-08-07:
400 Input tokens exceed the configured limit of 272000 tokens.
Your messages resulted in 273263 tokens.
```

At that point the fallback mechanism moved execution to `AnthropicBedrockAdapter`. The issue solver had `toolOrder` configured on the thread — a per-turn tool ordering feature that `BaseLLMAdapter` checks for adapter support before allowing. `AnthropicBedrockAdapter` does not implement this capability, so `BaseLLMAdapter` throws immediately on every attempt:

```
Tool ordering is not supported by AnthropicBedrockAdapter.
Only OpenAI adapter currently supports per-turn tool ordering.
```

`TerminalVelocityRetry` attempted the Anthropic path three times, got the same throw each time until it ran out of retries:

```
2026-01-05 16:39:12.073 WARN services/terminal-velocity-retry.service.ts:94
[TerminalVelocityRetry] Issue Solver (runId: 5a50c084-e6ff-44aa-a47a-decbc0caf9bd) failed
{ attempt: 3, maxAttempts: 3, error: 'Tool ordering is not supported by AnthropicBedrockAdapter.
Only OpenAI adapter currently supports per-turn tool ordering.', willRetry: false }

2026-01-05 16:39:12.073 ERROR services/terminal-velocity-retry.service.ts:135
[TerminalVelocityRetry] Issue Solver (runId: 5a50c084-e6ff-44aa-a47a-decbc0caf9bd) failed after 3 attempts
{ finalError: 'Tool ordering is not supported by AnthropicBedrockAdapter.
Only OpenAI adapter currently supports per-turn tool ordering.' }

2026-01-05 16:39:12.082 ERROR workers/issue-solver.worker.ts:114
Job 128837 has failed with Issue Solver (runId: 5a50c084-e6ff-44aa-a47a-decbc0caf9bd)
failed after 3 attempts: Tool ordering is not supported by AnthropicBedrockAdapter.
Only OpenAI adapter currently supports per-turn tool ordering.
```

The failure chain in order:

1. OpenAI hits token limit (273,263 > 272,000) — retries exhausted on OpenAI
2. Fallback activates `AnthropicBedrockAdapter`
3. `BaseLLMAdapter` checks `toolOrder` support — `AnthropicBedrockAdapter` does not support it — throws immediately
4. All 3 `TerminalVelocityRetry` attempts fail identically
5. `TerminalVelocityRetryableError` surfaces as the final error — this is the retry wrapper, not the root cause

#### Fix

Either add `toolOrder` support to `AnthropicBedrockAdapter` so the fallback path can honour the same thread configuration as OpenAI, or strip `toolOrder` from the thread before handing off to an adapter that does not support it.
