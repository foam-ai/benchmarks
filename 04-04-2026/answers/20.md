### RCA: `forceRemoveWorktreeDirectory()` deleted the filesystem directory but left git's `.git/worktrees/` metadata intact, causing `git worktree add` to fail with "missing but already registered" on retry

#### TL;DR

`createWorktree()` in `mewtwo/src/services/git-worktree.service.ts` calls `directoryExists()` to decide whether to skip or run `git worktree add`. When a previous `removeWorktree()` call failed and fell through to `forceRemoveWorktreeDirectory()`, the filesystem directory was deleted but git's internal `.git/worktrees/<name>/` registry entry was not cleaned up. On the next `createWorktree()` invocation for SHA `f175628105d88fb710838e61f5570bbe5734fac5`, `directoryExists()` returned `false` (directory is gone), so the code proceeded to `git worktree add` — which found the path registered but missing in `.git/worktrees/` and threw `fatal: '...' is a missing but already registered worktree`. First seen `2026-01-11T08:08:28.328Z`; recurred `2026-03-02T15:48:39.359Z`.

#### What Broke and Why

`removeWorktree()` has two code paths for cleanup. The happy path — `git worktree remove` — removes both the filesystem directory and the `.git/worktrees/<name>/` metadata atomically. The fallback path — `forceRemoveWorktreeDirectory()` — is reached when `git worktree remove` fails; it calls `fs.rm(worktreePath, { recursive: true, force: true })` to remove the directory but has no corresponding call to `git worktree prune`, leaving an orphaned entry in `.git/worktrees/` that points to a now-missing path.

`createWorktree()` guards against re-creation using a filesystem check (`directoryExists()`), not a registry check. After `forceRemoveWorktreeDirectory()` ran, the filesystem check returned `false` — the directory was gone — so `createWorktree()` proceeded to `git worktree add`. Git internally validates new worktree paths against `.git/worktrees/` before creating anything on disk. Finding an entry whose stored path no longer exists, it refuses with:

```
Command failed: git worktree add "/tmp/tv-worktrees/674e5380f251f603c5ef1847/foam-ai-all-the-things/f175628105d88fb710838e61f5570bbe5734fac5" "f175628105d88fb710838e61f5570bbe5734fac5"
Preparing worktree (detached HEAD f1756281)
fatal: '/tmp/tv-worktrees/674e5380f251f603c5ef1847/foam-ai-all-the-things/f175628105d88fb710838e61f5570bbe5734fac5' is a missing but already registered worktree
use 'add -f' to override
```

`baseRepo` was declared as `const` inside the `try` block in `removeWorktree()`, so the `catch` had no access to it — making it structurally impossible to call `git worktree prune` in the fallback path even if the code had tried. The same split-state could also arise from an interrupted `git worktree add` that wrote a `.git/worktrees/<name>/` entry but crashed before finishing the directory, or from `removeWorktree()` short-circuiting early when the directory was already absent (returns without touching the registry).

#### Fix

Hoist `baseRepo` out of the `try` block in `removeWorktree()` so the `catch` can reach it, then call `git worktree prune` before `forceRemoveWorktreeDirectory()`:

```diff
  async removeWorktree(worktreePath: string): Promise<void> {
-   try {
-     const baseRepo = path.dirname(gitDir);
+   let baseRepo: string | null = null;
+   try {
+     baseRepo = path.dirname(gitDir);
      // ...
    } catch (error) {
+     if (baseRepo) {
+       await this.pruneWorktreeMetadata(baseRepo);
+     }
      await this.forceRemoveWorktreeDirectory(worktreePath, error);
    }
  }
```

This ensures the `.git/worktrees/<name>/` registry entry is always pruned before the filesystem cleanup, keeping git's internal state and the filesystem in sync regardless of which removal code path runs.
