### RCA: E11000 Duplicate Key Error Is Expected

#### TL;DR

This exception is not a bug. The E11000 duplicate key error is the intentional behavior of the distributed locking mechanism. Two concurrent webhook requests arrived for the same resource, and MongoDB's unique index correctly prevented both from holding the lock simultaneously. The second request waited, retried, acquired the lock, and completed normally.

#### What Happened and Why

Two Sentry webhook requests arrived concurrently for the same resource (`customerId: 68225b7c65937a6a6f391d1d`, `resourceId: 7202529779`). Both attempted to insert a lock document into MongoDB, which has a unique index on `(customerId, type, resourceId)`. The first request won — the second hit the duplicate key error:

```
E11000 duplicate key error collection: foam_db.lock
index: customerId_1_type_1_resourceId_1
dup key: { customerId: ObjectId('68225b7c65937a6a6f391d1d'), type: "webhook", resourceId: "7202529779" }
```

This is exactly how the mutex is supposed to work. The unique index enforces mutual exclusion at the database level. The `withLock` function in `lock.service.ts` catches `MongoServerError` with code `11000`, logs it at `DEBUG` level (not `ERROR`), waits 1 second, and retries. The logs confirm the full happy path executed correctly:

```
23:20:32.502 DEBUG  Lock already exists for customerId: 68225b7c65937a6a6f391d1d and resourceId: 7202529779
23:20:33.503 DEBUG  Attempting to create lock ... (retry after 1s wait)
23:20:33.527 DEBUG  Acquired lock for customerId: 68225b7c65937a6a6f391d1d and resourceId: 7202529779
23:20:33.527 INFO   Received and ignored webhook action
23:20:33.571 DEBUG  Released lock for customerId: 68225b7c65937a6a6f391d1d and resourceId: 7202529779
```

The second request waited exactly 1 second (`23:20:32.502` → `23:20:33.503`), acquired the lock once the first released it, processed the webhook (which it correctly ignored as an `event_alert` action), and released the lock cleanly. The entire flow took ~1.1 seconds.

#### Fix

None required — the lock mechanism is functioning as designed.

Alternate ways to implement a valid lock that remove the exception are also valid.

#### Grading Notes: Acceptable Alternative Analyses

The critical requirement is identifying that the E11000 is **expected and handled** by `withLock`, not an unhandled failure. The following alternative framings are also acceptable if they reach that conclusion:

**OTEL instrumentation noise (accept as valid enhancement, not a bug fix):**
A response that correctly identifies the root cause AND additionally explains that `@opentelemetry/instrumentation-mongodb` records the E11000 as a span exception at the driver level *before* the application catch block runs — surfacing handled errors as alerts — is a valid deeper analysis. This is a real operational concern, not a bug. Proposed mitigations may include:

**What is NOT acceptable:**
- Treating the E11000 as an unhandled error or a bug in the lock implementation
- Proposing a fix without recognizing the error is already caught and retried
- Claiming the lock mechanism is broken or data was corrupted
- Missing that the logs show a complete successful retry cycle
