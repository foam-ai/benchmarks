### RCA: `generateRcaSummary` failing with 404 in `mewtwo/src/llms/ai-sdk/registry.ts`

#### TL;DR

`generateRcaSummary` always fails with a 404 `Resource not found` because the `perla-mbgwr1sv-eastus2` Azure resource does not serve the deployment-based responses path (`/openai/deployments/{id}/responses`) that `registry.ts` was configured to call. The SDK configuration itself — `useDeploymentBasedUrls: true` with `apiVersion: '2024-12-01-preview'` — is [valid per the AI SDK docs](https://ai-sdk.dev/providers/ai-sdk-providers/azure), but this specific Azure resource only serves the `responses` API via v1-style endpoints (`/openai/v1/responses`), not via the deployment-based path. The `2024-12-01-preview` API version does not support the deployment-based responses path on this resource.

#### What Broke and Why

The configuration in `mewtwo/src/llms/ai-sdk/registry.ts` at the time of the incident:

```typescript
const azureGPT5 = createAzure({
  apiKey: AZURE_OPENAI_API_KEY_GPT_5,
  baseURL: azureGPT5BaseURL,
  apiVersion: '2024-12-01-preview',
  useDeploymentBasedUrls: true,
});

return logged(Step.LLM_CALL_AZURE, azureGPT5(deploymentName));
// → constructs: /openai/deployments/gpt-5-mini/responses?api-version=2024-12-01-preview
```

**Why it broke:** The `perla-mbgwr1sv-eastus2` Azure resource only serves [v1-style endpoints](https://learn.microsoft.com/en-us/azure/foundry/openai/api-version-lifecycle) (`/openai/v1/responses`). `generateRcaSummary` was introduced in [PR #305](https://github.com/foam-ai/all-the-things/pull/305) and the deployment-based path was never validated against this resource before it went to production. While the resource does serve the `responses` API, the `2024-12-01-preview` API version used in the deployment-based URL is not supported on this resource.

Both paths were verified directly against the resource:

```bash
# Deployment-based responses path → confirmed 404 on perla-mbgwr1sv-eastus2
curl -sS -w "\nHTTP %{http_code}\n" \
  "https://perla-mbgwr1sv-eastus2.cognitiveservices.azure.com/openai/deployments/gpt-5-mini/responses?api-version=2024-12-01-preview" \
  -H "Content-Type: application/json" \
  -H "api-key: $AZURE_OPENAI_API_KEY_GPT_5" \
  -d '{"model": "gpt-5-mini", "input": [{"role": "user", "content": "hi"}]}'
# → HTTP 404

# v1-style responses path → confirmed 200 on perla-mbgwr1sv-eastus2
curl -sS -w "\nHTTP %{http_code}\n" \
  "https://perla-mbgwr1sv-eastus2.cognitiveservices.azure.com/openai/v1/responses?api-version=v1" \
  -H "Content-Type: application/json" \
  -H "api-key: $AZURE_OPENAI_API_KEY_GPT_5" \
  -d '{"model": "gpt-5-mini", "input": [{"role": "user", "content": "hi"}]}'
# → HTTP 200
```

#### Fix

Switch `registry.ts` to use the v1-style endpoint that `perla-mbgwr1sv-eastus2` does serve:

1. Change `AZURE_API_VERSION` to `'v1'`
2. Remove `useDeploymentBasedUrls: true` from both `azureStandard` and `azureGPT5`
3. Replace hardcoded `apiVersion: '2024-12-01-preview'` in `azureGPT5` with `AZURE_API_VERSION`
4. Change both callers from `provider(deploymentName)` to `provider.responses(deploymentName)`

**Alternative fix:** Keep the existing `apiVersion: '2024-12-01-preview'` and `useDeploymentBasedUrls: true` configuration, but use the chat completions API (`/openai/deployments/{id}/chat/completions`) instead of the responses API. The deployment-based chat completions path does work on `perla-mbgwr1sv-eastus2` with the current API version — only the responses path returns 404.
