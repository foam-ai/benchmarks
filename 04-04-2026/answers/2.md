### RCA: Redis ElastiCache Hit maxmemory Limit, Causing BullMQ Issue-Solver Jobs to Fail with OOM

#### TL;DR

Jobs on the `issue-solver-queue` in the **mono** service were failing immediately after being picked up because the BullMQ Redis instance (`redis://redis-bullmq-1.c4lpp0.ng.0001.usw1.cache.amazonaws.com:6379`) had reached its `maxmemory` limit. With a `noeviction` policy in place, Redis rejected all writes including the Lua scripts BullMQ uses to manage job state. Memory was exhausted by two compounding sources: `issue-solver-queue` accumulating job data with no cleanup policy, and `terminal-velocity-queue` accumulating unprocessed jobs with no worker consuming them. Evals were unaffected because they invoke the issue solver directly, bypassing the Redis queue entirely.

#### What Broke and Why

At `07:04:55` and `07:05:10` UTC, BullMQ attempted to extend active job locks for jobs `130236` and `130237`:
```
db.statement: evalsha cc4eded989ba9b04d25cc2407a1142f33a30400e 1
  bull:issue-solver-queue:stalled
  bull:issue-solver-queue:
  130236 130237 30000

Error: OOM command not allowed when used memory > 'maxmemory'.
  script: cc4eded989ba9b04d25cc2407a1142f33a30400e, on @user_script:26.
```

Redis was at capacity and refused the write. BullMQ's `extendLocks` operation — which keeps active jobs alive by periodically refreshing their lock TTL — could not complete, causing the jobs to be marked stalled and ultimately failed.

The failure path:
- Worker picks up job and begins processing
- BullMQ periodically calls `extendLocks` to keep the job's lock alive in Redis
- Redis rejects the Lua script with `OOM command not allowed when used memory > 'maxmemory'`
- Job fails — `solveIssue()` never gets far enough to call any LLM
- `FOAM_ISSUE_SOLVE_SUCCEEDED` drops to zero; Azure OpenAI request count drops to zero
- Evals continue working because `runIssueSolver(runId)` calls the solver directly without touching the Redis queue

**Issues:**

**1. `issue-solver-queue` — missing cleanup configuration.** The queue is initialized without `removeOnComplete` or `removeOnFail`, meaning every completed and failed job's full data hash persists in Redis indefinitely. This is also an issue for the `terminal-velocity-queue`.

**2. `terminal-velocity-queue` — no worker consuming it.** Telemetry shows zero `process` spans for this queue across every day in January, while jobs were being actively enqueued throughout — 205 adds on Jan 28 and 37 on Jan 29 alone. With no worker consuming them, jobs sit permanently in the waiting state with no path to cleanup. In addition, unlike `issue-solver-queue` which stores only a `runId`, `terminal-velocity-queue` payloads carry the full task specification inline — prompts, harness args, and serialized tracing spans — making each unprocessed job substantially larger in Redis. All queues share the same Redis instance, so memory pressure from one queue directly starves every other queue of write capacity.

With `maxmemory-policy` set to `noeviction` (required for BullMQ correctness), Redis has no self-healing capacity. The combination of these two sources gradually filled the instance until any write — including the routine `extendLocks` operation — triggered the OOM rejection.

#### Fix

**Immediate:** Drain the unprocessed `terminal-velocity-queue` and purge stale `issue-solver-queue` job data without affecting live jobs:
```typescript
import { Queue } from 'bullmq';
import { getRedisConnectionConfig } from './src/keys';

async function cleanup() {
  const connection = getRedisConnectionConfig();

  const tvQueue = new Queue('terminal-velocity-queue', { connection });
  await tvQueue.obliterate({ force: true });
  console.log('terminal-velocity-queue obliterated');

  const isQueue = new Queue('issue-solver-queue', { connection });
  await isQueue.clean(3600000, 0, 'completed');
  await isQueue.clean(86400000, 0, 'failed');
  console.log('issue-solver-queue cleaned');

  await tvQueue.close();
  await isQueue.close();
}

cleanup().catch(console.error);
```

Run with:
```bash
npx tsx scripts/cleanup-redis.ts
```

**Permanent:** Add `removeOnComplete` and `removeOnFail` to all queue definitions in `mono`:
```typescript
defaultJobOptions: {
  removeOnComplete: { age: 3600, count: 1000 },
  removeOnFail: { age: 86400, count: 5000 },
}
```
