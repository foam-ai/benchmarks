### RCA: Missing `command` Field in Added BullMQ Eval Job

#### TL;DR

A job was added to the BullMQ `eval-queue` with empty job data — `{}` — omitting the `command` field required by `EvalJobData`. The worker validation caught this immediately and failed the job. No code is broken; the job was simply enqueued incorrectly.

#### What Broke and Why

The eval worker in `mewtwo/src/workers/eval.worker.ts` requires all jobs to carry a `command` field, enforced by an explicit guard at line 42–43:
```typescript
// mewtwo/src/workers/eval.worker.ts — line 42-43
const { command } = job.data;

if (!command) {
    throw new Error('Job data must include "command" field');  // ← line 43
}
```

The job was added with no data payload, as confirmed by the worker log:
```
2026-01-16 23:26:25.910 INFO src/workers/eval.worker.ts:37
[eval-worker] Processing eval job 19 {}
```

The empty object `{}` means `command` destructures as `undefined`, the guard fires immediately, and BullMQ marks the job as failed:
```
bullmq.job.failed.reason: "Job data must include \"command\" field"

exception.type:    Error
exception.message: Job data must include "command" field
    at MonitoredWorker.concurrency (mewtwo/src/workers/eval.worker.ts:43)
    at MonitoredWorker.retryIfFailed (bullmq/src/classes/worker.ts:1251)

[eval-worker] Job 19 failed: Job data must include "command" field
2026-01-16 23:26:25.930 ERROR src/workers/eval.worker.ts:138
[eval-worker] Job 19 failed { error: 'Job data must include "command" field' }
```

The `EvalJobData` interface requires `command` to be present:
```typescript
export interface EvalJobData {
    command: string;  // ← required and was not included in the added job
}
```

The worker validation worked exactly as intended. The failure is purely an operational error — not a code defect.

#### No Code Changes Required

The code is working as expected. The `command` guard in the worker correctly rejected a malformed job, which is the designed behavior. There is no bug to fix and no code change needed.

Critically, **nothing in this repository enqueues jobs into the eval queue**. The two relevant files are:

- `mewtwo/src/queues/eval.queue.ts` — defines the queue and the `EvalJobData` interface
- `mewtwo/src/workers/eval.worker.ts` — consumes and processes jobs from the queue

No file in the entire repo imports `evalQueue` to call `.add()`. No router, service, script, bin file, or workflow enqueues jobs into it. The queue infrastructure (definition + worker) was built out, but the producer side was never wired up in this codebase. Evals are run directly via the CLI (`yarn mewtwo run eval run ...`) both in the GitHub Actions workflow and locally.

This means the job was added from **outside this repository** — either by another service, an external script, or manually via a Redis client or dashboard.

#### Prevention

When adding a job to the `eval-queue`, always include the `command` field. The `command` value is a shell string that the worker spawns as a child process from the `mewtwo/` directory — it is the same command you would run locally via the eval CLI:
```typescript
//  Example to run a specific eval
await evalQueue.add('eval-job', {
    command: 'yarn eval run foam-eval-worker-missing-command-field',
});

// Example to run all evals under a specific experiment
await evalQueue.add('eval-job', {
    command: 'yarn eval run --experiments deep-research-5-phases',
});
```

If jobs are being added manually (e.g. via a Redis CLI, dashboard, or ad-hoc script), ensure the data payload includes `{ "command": "<shell command>" }` before enqueuing.
